3  The server

fxmenet-server is a console program with no window. It hosts plugins for any number of clients at once, as far as the CPU allows.

3.1  Command line

fxmenet-server [--name NAME] [--control-port N] [--udp-port N] 
               [--discovery-port N] [--no-discovery] 
               [--plugin-path DIR]... [--no-default-paths] [--rescan] 
               [--remote-admin]

Option

Meaning

--name NAME

The name shown to clients. Default: the computer’s name.

--control-port N

TCP port for control. Default 54322.

--udp-port N

UDP port for audio. Default 54321.

--discovery-port N

UDP port answering Find. Default 54320.

--no-discovery

Do not answer Find. Clients must then type the address.

--plugin-path DIR

Also search this folder, for this run only. May be repeated.

--no-default-paths

Do not search the standard VST3 folders, for this run only.

--rescan

Ignore the plugin cache and examine every plugin again.

--remote-admin

Let fxmenet-top change the plugin folders from other machines (section 3.8).

The server logs to its standard output, with a time stamp on each line, so a service manager (such as systemd’s journal) collects it.

3.2  Which plugins the server offers

The server offers VST3 effects. Instruments are skipped. A plugin bundle that holds several plugins (a suite) offers each of them.

Each plugin file is examined in a separate process. A plugin that crashes or hangs while it is loaded is logged, skipped, and does not take the server down. It stays skipped until the file changes. The results are kept in a cache file (fxmenet-server-plugins.xml, in the FX-Mechanics folder of the user’s configuration directory), keyed by the file’s path, size and date, so only new or changed plugins are examined at the next start. This examination also notes whether the plugin is made for FxmeNet (chapter 9).

If the same plugin is installed in two folders, the first one found is used.

3.3  Plugin folders

The server searches three kinds of folders:

Default folders.

The standard VST3 folders of the operating system. They can be turned off.

Saved folders.

Folders you add with fxmenet-top (chapter 4). The server remembers them from one run to the next, in fxmenet-server-settings.json beside the cache file.

This run’s folders.

Those given with --plugin-path. They are not remembered.

Folders are searched with their subfolders. After a change of folders, or when you install a plugin while the server runs, ask for a rescan in fxmenet-top. The scan runs in the background; the sessions in progress keep playing. A client sees the new list the next time it connects.

3.4  Ports and discovery

The server listens on three ports (chapter 12). Find in the plugin broadcasts a question on the discovery port, and every server answers with its name, system and number of sessions. Broadcasts normally stay inside one network segment: across routers or VPNs, type the address. Only one server can run on a machine with discovery on; a second one says so in its log and runs without it.

3.5  Sessions

A session starts when a client connects and ends when it says goodbye. If a client’s connection drops (a network hiccup, a DAW that crashes), the server keeps the session for 10 seconds, so that the client can resume it without losing its chain.

Each session has its own audio thread. The server asks the operating system to run it with real-time priority; if the system refuses, the server logs a warning and runs it as an ordinary thread, which is less reliable under load (section 7.4).

3.6  Reading the log

At startup the log lists the plugins found. Every 10 seconds, for each session that is working, it prints one line of figures (the numbers below are an example): 

session 3: 8123 blocks, lost 0, stale 0, from cache 0, queue full 0, 
send errors 0, resets 1 | process 412 us, max 10 s 1180 us, max 2310 us | 
turnaround max 10 s 1650 us, over 1 block 0, over 2 blocks 0 | 
chain latency 256, telemetry frames 240, parameter changes 12

Counts are since the session started; the values marked 10 s cover the last interval.

Figure

Meaning

blocks

Blocks processed.

lost

Blocks that never arrived in time: the server skipped them (the client conceals them).

stale

Late blocks too old to answer, dropped.

from cache

Duplicate requests answered from the server’s cache of recent replies.

queue full

Requests refused because the session could not keep up.

send errors

Replies the system refused to send, typically because the send buffer was full (section 7.4).

resets

Times the client asked to restart the chain’s audio (transport start, stop or jump).

process

Time spent processing the last block, then the worst in the last 10 seconds, then the worst since the start.

turnaround

Time from a request’s arrival to its reply leaving, worst of the last 10 seconds.

over 1 block, over 2 blocks

Replies that left more than one (two) block durations after the request arrived: the server fell behind.

chain latency

Latency of the chain, in samples.

A process time that gets close to the block’s duration (2.9 ms for 128 samples at 44.1 kHz) means the server is running out of CPU for that session.

3.7  Running the server as a service

Below is an example of a systemd unit for Linux. Running the server as a service is a possibility that has not been tested yet, so treat the example as a starting point. Feedback is welcome, and so are equivalents for other systems (launchd on macOS, a Windows service). 

[Unit] 
Description=FxmeNet server 
After=network-online.target 
Wants=network-online.target 
 
[Service] 
ExecStart=/usr/local/bin/fxmenet-server 
User=fxmenet 
Group=audio 
Restart=on-failure 
LimitRTPRIO=95 
LimitMEMLOCK=infinity 
 
[Install] 
WantedBy=multi-user.target

3.8  Letting a remote fxmenet-top change the folders

fxmenet-top can watch a server from any machine of the network. It may change the plugin folders only when it connects from the server’s own machine, unless you start the server with --remote-admin. Because the network is not authenticated, use this option only on a network you trust.
